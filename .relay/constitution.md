# Security Rules

These rules are **mandatory**. Every change touching system boundaries, authentication, or dependency management must follow them.

## Input Validation

- Validate all input at system boundaries (API endpoints, message consumers, file parsers) before any processing.
- Use allowlists over denylists — reject anything not explicitly permitted.
- Sanitize user-supplied data before rendering in HTML, SQL, shell commands, or log output.
- Enforce size limits on request bodies, file uploads, and query parameters.

## Authentication and Authorization

- Authenticate every request to a protected resource; never rely on client-side checks alone.
- Use short-lived tokens (JWT, OAuth2) and rotate secrets on a defined schedule.
- Apply the principle of least privilege — grant the minimum permissions needed for each role or service.
- Separate authentication (who you are) from authorization (what you may do) in code structure.

## Secrets Management

- Never hardcode secrets, API keys, or credentials in source code or config files checked into version control.
- Load secrets from environment variables or a dedicated secret store (Vault, AWS Secrets Manager, etc.).
- Add secret patterns to `.gitignore` and use pre-commit hooks or CI scans to catch accidental commits.
- Rotate compromised or leaked secrets immediately; treat any secret committed to a repo as compromised.

## Dependency Security

- Review new dependencies before adding them — check maintenance status, known vulnerabilities, and license.
- Pin dependency versions in lock files; avoid floating ranges in production.
- Run automated vulnerability scanning (e.g., `npm audit`, `pip-audit`, Dependabot) in CI on every PR.
- Remove unused dependencies promptly to reduce attack surface.

## OWASP Top 10 Awareness

- Guard against injection (SQL, NoSQL, OS command) by using parameterized queries and safe APIs.
- Protect against broken access control by enforcing permissions server-side on every request.
- Avoid security misconfigurations — use secure defaults, disable debug modes in production, and review HTTP headers.
- Log security-relevant events (failed logins, permission denials, input validation failures) for monitoring and audit.

# Testing Rules

These rules are **mandatory**. All production code must have meaningful test coverage following these guidelines.

## TDD Expectations

- Write tests before implementation when feasible — especially for new endpoints, business logic, and bug fixes.
- When fixing a bug, first write a test that reproduces the failure, then fix the code.
- Use tests to clarify requirements before writing implementation code.
- If writing tests first is impractical (e.g., exploratory prototyping), add tests immediately after the code stabilizes.

## Test Naming Conventions

- Name tests to describe the expected behavior, not the implementation: `rejects expired tokens` not `test_check_token_expiry`.
- Group related tests under descriptive blocks (e.g., `describe("payment processing")` or test class names).
- A failing test name should tell you what broke without reading the test body.
- Avoid generic names like `test1`, `testHelper`, or `testItWorks`.

## Coverage Expectations

- Aim for meaningful coverage of behavior, not a specific percentage target.
- Every public API endpoint must have at least one happy-path and one error-path test.
- Critical business logic (payments, auth, data transforms) must have thorough edge-case coverage.
- Coverage tools are informational — use them to find gaps, not as a gate to game.

## Test Isolation

- Each test must be independent — no shared mutable state between tests.
- Use setup/teardown hooks to create and destroy test fixtures; never rely on test execution order.
- Mock or stub external services (databases, APIs, file systems) to avoid flaky network-dependent tests.
- Tests must produce the same result regardless of the order they run in.

## Integration vs Unit Tests

- Unit tests cover a single function or module in isolation with mocked dependencies.
- Integration tests verify that components work together (e.g., API route through to database).
- Prefer a testing pyramid: many unit tests, fewer integration tests, minimal end-to-end tests.
- Run unit tests on every commit; run integration tests on every PR. Reserve E2E tests for deploy pipelines.
